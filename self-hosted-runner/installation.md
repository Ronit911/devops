# Self-Hosted Runner Installation

A self-hosted runner requires a supported machine and the GitHub Actions runner software.

This section describes the general installation process used for a Linux deployment server.

## Prerequisites

The server should have:

- Linux operating system
- Network connectivity
- Appropriate permissions
- Required application dependencies
- Access to the GitHub repository
- Sufficient disk space

The exact requirements depend on the workflow.

## Installation Flow

The general process is:

Server
    |
    v
Create Runner Directory
    |
    v
Download Runner Package
    |
    v
Extract Runner
    |
    v
Configure Runner
    |
    v
Install Service
    |
    v
Start Runner

## Example Directory

A dedicated directory can be used:

/opt/actions-runner

The actual location can be different depending on the deployment design.

## Downloading the Runner

GitHub provides the runner package for supported operating systems and architectures.

The installation process generally involves:

1. Creating a directory.
2. Downloading the runner package.
3. Verifying the package when appropriate.
4. Extracting the package.
5. Configuring the runner.
6. Connecting it to the repository or organization.

## Configuration

The runner configuration associates the runner with GitHub.

The configuration process requires a temporary registration token generated by GitHub.

The token should not be stored permanently in documentation or source control.

## Running the Runner

A runner can initially be tested interactively.

The runner process waits for jobs from GitHub.

For example, conceptually:

Runner
    |
    v
Waiting for Jobs
    |
    v
Job Received
    |
    v
Execute Job
    |
    v
Return Result
    |
    v
Waiting for Jobs

## Running as a Service

For a deployment server, the runner can be installed as a system service.

This allows it to:

- Start automatically
- Run without an interactive SSH session
- Restart after a server reboot
- Operate continuously

Typical service management uses systemd on Linux.

Example commands:

sudo systemctl status <runner-service>

sudo systemctl start <runner-service>

sudo systemctl stop <runner-service>

sudo systemctl restart <runner-service>

The exact service name depends on the runner configuration.

## Hands-On Observation

During the runner work, the Linux server was checked for the runner process.

A process listing can be used to identify the runner:

ps -ef | grep '[R]unner.Listener'

This helps verify whether the runner process is active.
